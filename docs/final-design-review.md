## 구현과의 차이

| 항목 | 최종 PDF | 현재 main의 기초 범위 / 후속 작업 |
| --- | --- | --- |
| 큰 흐름 | 기술 → 3관점 병렬 → 종합 → 보고서 | 같은 구조 구현 |
| 호출 API | 질문을 호출자가 하나씩 전달 | 목록을 한 번 받아 내부에서 모든 질문 순회. 기술/질문별 예산 보존 |
| 실행 한도 | 검색 3, 답변 수정 1, 종합 보완 1 | 사용자와 선택한 간소화안: 검색 3, 별도 수정/종합 보완 0 |
| 논문 corpus | target 2 + reference 2 | target 2 기본 제공. reference corpus 등록·검증은 검색 담당 후속 작업 |
| 도메인 필터 | target만 | 현재 target+reference 허용. 최종 정책에 맞추려면 필터를 함께 변경하고 검증 필요 |
| 이해관계자 | 웹 + 제한적 reference 조회 | 현재 웹 + 상위 원문 전달. 새로운 reference 검색은 없음 |
| 검색 품질 | 3개 모델·30문항, Hit@5 ≥ .80 / MRR ≥ .60 | 목표값이며 현재 플랫폼에서 측정 완료한 성능 아님 |
| 시장 항목 | 성장/채택/생태계 3개 | 6질문 및 등급·C.2·C.4·표 8 반영. 아래 제출본 정렬 참조; 실제 LLM 준수 검증은 남음 |
| 이해관계자/도메인 세부 항목 | 주체 3개 / 기준 5개 | 현재 초기 rubric 범위가 더 작음. 각 담당자가 확대해야 함 |
| TRL | 기술에서 잠정, 종합에서 확정 | 현재 정성적 maturity 기준. 별도 trl_result/1–9 판정 미구현 |
| 출력 | SUMMARY–REFERENCE PDF 및 인용 검사 | 개발용 JSON/Markdown, 인수용 서지 검사. 제출 PDF 출력은 후속 작업 |

최종본을 기준으로 개발한다고 소개하려면 이 차이표를 닫아야 합니다.
기존 사용자의 간소화 선택을 최종 PDF만으로 바꾸지 않았습니다. 자동 보완을 다시 넣을지는 별도 범위 결정입니다.

## 시장 rubric 1단계 구체화

[과제 지시서](https://actually-war-1ea.notion.site/KV-cache-3ba7f4c866938099b7a8fdaa1831c07e)의 시장 규모·성장성, 상용화·채택, 생태계 지지 범위와 중립적 비교 목적을 기준으로
`rubrics/market.yaml`의 판정 조건을 구체화했습니다. 기존 criterion ID와 허용 판정값, 공통 스키마는 유지합니다.

- 성장성: 시장 범위·지역·기간·수치 단위를 구분하고, 비교 가능한 전망의 상충과 단순 정보 부족을 분리합니다.
- 채택: 계획·연구 시연과 실제 파일럿·정식 출시·운영을 구분하며, 정식 출시만으로 대규모 운영을 추정하지 않습니다.
- 생태계: 기술 동일성·지원 버전/범위·정식/실험적 상태를 확인하고 일반 KV 양자화/CXL 지원을 선정 기술 지원으로 전용하지 않습니다.
- 출처: 평가 기준일·자료 시점·이해당사자 편향·상충·미확인을 보존하며 입력 근거의 메타데이터를 임의로 변경하지 않습니다.

PDF 표 8의 높음/보통/낮음 및 출처 개수 기반 규칙과의 차이는 여전히 남아 있습니다.
이번 변경은 기존 코드의 근거 상태형 판정을 구체화한 것이며, PDF 수정이나 팀 전체의 최종 등급 합의를 의미하지 않습니다.
현재 로컬 제공 PDF의 C.2에는 이 문서의 '최종본에 반영된 개선'에 적힌 직접 근거/분야 배경 구분 문구가 보이지 않으므로 기준 PDF 버전 확인도 필요합니다.
프롬프트 구조·실행 질문·검색·그래프·Judge는 이번 단계에서 변경하지 않았습니다.
기존 프롬프트가 rubric을 읽으므로 생성 지침에는 반영되지만, 실제 LLM의 판정 품질은 고정 근거 평가와 사람 검수로 확인해야 합니다.

시장 `basic.json`과 `acceptance.json`은 두 기술 × 세 기준의 6개 질문을 사용하며, 질문마다 필요한 사실과 조건을 구체화했습니다.
따라서 basic을 읽는 기존 전체 파이프라인에서도 시장 6개 항목을 요청합니다. 기존 질문 ID와 공통 스키마는 유지합니다.
description의 평가 기준일 2026-09-22는 재현 가능한 고정 예시이며, 실제 평가에서는 기준일과 근거를 함께 교체해야 합니다.
발췌 evidence는 연결 점검용으로 유지했습니다. 실제 시장 근거 구성과 6항목 근거 부족·오판 경계 사례는 4단계에 남아 있습니다.
기본 질문 수와 배열 순서에 의존하던 테스트를 조정하고, 전체 파이프라인에서 시장 6개 항목이 종합에 전달되는지 확인합니다.

## 시장 고정 근거 4단계 구성

`tests/fixtures/market`에 정상 근거·도입 계획·분야 배경·중복 발표·상충 전망·유사 구현·메타데이터 누락·상위 결과 불일치의
합성 사례 8개를 추가했습니다. `missing-evidence.json`도 6개 질문으로 확장했습니다.
합성 자료는 fixture 유형·SYNTHETIC 표기·example.invalid URL로 구분하며 실제 기술 근거로 사용하지 않습니다.
기대 판정과 검토 항목은 Generator 입력과 분리된 `expectations.json`에, 실행법과 해석상의 한계는 같은 디렉터리의 README에 기록했습니다.
현재 MockBackend는 근거가 없으면 assessment를 생략하므로 missing-evidence의 6개 확인 불가 생성 성공을 mock으로 증명할 수 없습니다.
실제 LLM에 대한 의미적 평가 및 시장 전용 자동 검증은 후속 작업이며, 이번 자료 작성으로 검색·판정 품질을 측정했다고 보지 않습니다.

위 1~4단계 기록은 당시 변경 이력입니다. 현재 시장 rubric은 세 항목 모두 표 8의 높음/보통/낮음/확인 불가를 사용합니다.

소속·관계를 모르면 추정하지 않으며 별도 공통 스키마 필드를 추가하지 않았습니다.

## 제출 설계서 (2).pdf 기준 시장 규칙 정렬 (현재 적용)

- C.2의 애매하면 낮은 등급, C.4의 계획만 확인되면 한 등급 하향을 프롬프트에 반영했습니다.

- 정식 도입 1건을 자동 보통에 넣는 별도 매핑은 제거했습니다. 설계서가 개별 경계 사례를 모두 열거하지 않으므로 표 조건과 C.2에 따른 판단 사유를 기록합니다.
- 이해당사자 표시·직접/배경 구분·인용 ID 보존은 유지했고 합성 기대값을 갱신했습니다.

시장 프롬프트·rubric을 제출본 규칙으로 정렬한 것이며 실제 LLM 준수나 전체 설계 구현 완료를 의미하지 않습니다.
양쪽 검색의 수행 보장, 공통 그래프·State·종합·보고서 구현은 시장 담당 변경 범위 밖입니다.

## 1~4단계 재검토에서 발견한 오류 수정

표 8의 등급 조건 12개는 그대로 유지하고, 설계서에 없는 '계획이 실현됐다고 가정해 하향 전 등급 계산' 절차를 제거했습니다.
출시 계획 1건의 하향 전 등급은 설계서에 명시되어 있지 않으므로 planned-only를 실제 제품 출시 계획 사례로 바꾸고,
채택 기대값은 expectations.json에서만 null과 검토 이유로 표시했습니다. 자동 등급 정답으로 사용하지 않으며 실제 NodeResult의 네 등급 계약은 유지합니다.
supported는 서로 다른 도입 A-01·정식 기능 출시 C-02를 명시하고 채택 기대값을 높음으로 바로잡았습니다.
missing-metadata는 실험적 프레임워크·커뮤니티 구현의 지원·버전·범위가 명확하고 날짜만 누락된 사례로 변경했습니다.
지원 근거에 따른 등급과 날짜 미확인을 분리하며, 날짜 누락을 자동 확인 불가 조건으로 사용하지 않습니다.
실제 파이프라인이 읽는 basic 입력의 고정 기준일·이후 자료 차단 문구는 제거했습니다. acceptance와 합성 사례의 고정 날짜는 테스트 조건으로만 유지합니다.
이 수정은 1~4단계 산출물 보정이며 5단계 시장 전용 자동 검증이나 실제 LLM 품질 평가 완료를 의미하지 않습니다.

## 시장 5단계: 전용 오프라인 검증 추가

앞선 절의 시장 전용 자동 검증 미구현 기록은 이 절로 갱신합니다.
`app/evaluate_market.py`와 `tests/test_market_eval.py`를 추가했습니다.
기존 expectations.json의 13개 사례, 고정 등급 76개, 수동 검토 2개를 그대로 사용하며
새 등급 조건이나 그래프 노드를 추가하지 않습니다. 실행법은 시장 fixture README에 있습니다.

저장된 입력·근거 일치, 6항목 누락/중복, 등급 대조, 공통 인용 계약, 기술 간 잘못된 인용,
검색 이력·실패·미확인 상태를 검사합니다. planned-only의 채택 등급은 자동 정답으로 강제하지 않습니다.
인용 내용과 판단 사유의 의미, 이해당사자 표시·상충 설명 등은 기존 review_checks로 사람이 검토합니다.
자동 검사 통과와 무관하게 human_review_required를 유지합니다.

검증기 단위 테스트는 가공된 결과를 사용합니다. 실제 유료 LLM 평가·검색 품질 평가·최종 보고서 인수는
이 단계의 완료에 포함되지 않으며, 전체 설계나 공통 그래프의 차이를 해결했다고 선언하지 않습니다.

## 시장 재대조 후 보완: A.4·B.3·C.2

- A.4의 평가 범위를 시장 시스템 프롬프트에 명시했습니다. KIVI는 KV cache 양자화,
  ITME는 CXL 메모리를 KV cache 저장 계층으로 쓰는 접근의 대표 사례로 다룹니다.
  접근 전반의 동향과 선정 기술 자체의 채택·지원 근거는 C.2에 따라 구분합니다.
- B.3의 reference 활용과 C.2의 배경 근거 활용에 맞춰, 시장 검증기가 다른 기술명이라는
  이유만으로 배경·보조 문서 인용을 거부하던 제한을 수정했습니다. 해당 인용을 별도 사람 검토
  목록으로 반환하며, ID·Judge·기대 등급 검사는 유지합니다. 메타데이터만으로 인용의 의미를
  자동 승인하지 않으며 신규 등급 조건을 추가하지 않았습니다.
- C.2의 긍정·비판 자료 검색 요구를 시장 자료 정책과 basic/acceptance의 6개 질문에 반영했습니다.
  한쪽 자료만 제공되면 그 사실을 남기고, 실행 기록 없이 검색했다고 주장하지 않도록 했습니다.
  질문·프롬프트 반영만으로 검색 수행을 보장하지는 않습니다. 공통 검색의 양쪽 실행·기록 및
  종합의 gap 판단과 연결하는 작업은 담당 팀원과 통합할 사항으로 남습니다.

표 8의 12개 등급 조건과 기존 기대 판정은 유지합니다. 실제 LLM 평가와 사람의 원문 검토는 남아 있습니다.

## 역할 분담 의견

3개 평가 담당 + 검색 품질 담당 + 공통 기반 담당은 현재 플랫폼과 잘 맞습니다.
다만 ‘끝난 사람이 종합/보고서를 맡는다’만으로 두면 마지막 통합 책임이 비게 됩니다.
검색 품질 담당에게 기술 조사/원문 검수 책임을, 기반 담당에게 종합/보고서 연결 책임을 미리 두고,
세 평가 담당자가 완료 후 보고서 내용 검수에 합류하는 구성을 권합니다.
실제 개인 배정과 등급 합의는 [협업 계약](team-contract.md)의 경계를 기준으로 확정하면 됩니다.
